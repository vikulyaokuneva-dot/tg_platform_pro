# PETS 4.2 — аудит конвейера контента

Дата: 2026-10-26. Режим: offline-разработка; `PETS_PUBLISH=0`, Telegram,
cron и GigaChat не запускались. Production SQLite `pets-state` не менялась.

## Схема и фактический статус

```text
Разрешённый источник
  → candidate connector (PMC/Frontiers)
  → factual brief (DOI/PMCID, лицензия, факты, ограничения)
  → техническая + редакционная + safety validation
  → оригинальная генерация
  → проверка текста относительно facts
  → тематическая лицензированная фотография
  → pets_publication_queue (SQLite)
  → независимый durable/Telegram gate
  → Telegram
```

| Этап | Реализован | Использовался на production | Блокер / правило |
| --- | --- | --- | --- |
| Поиск PMC/Frontiers | да | нет | включается только `PETS_EXTERNAL_SOURCES=1` |
| Facts и лицензии | да | нет | CC BY/CC BY-SA/CC0/Public Domain и подтверждённая адаптация |
| Редакционный отбор | да | нет | бытовой контекст, польза владельцу, не медицинская тема |
| AI-генерация | да | нет | GigaChat только с отдельным opt-in и лимитом; mock всегда `review` |
| Проверка текста/фото | да | нет | неподтверждённое число, рискованный совет или неподходящее фото → review |
| Очередь | да, PETS 4.2 | нет | новая SQLite-таблица `pets_publication_queue`, только verified factual drafts |
| Публикация | да, старый evergreen путь | один исторический demo-пост №39 | новая factual очередь пока намеренно не подключена к отправке без отдельного запуска |

## Найденный разрыв и исправление

До 4.2 `run_autonomous_dry_run()` работал отдельно от основного PETS job:
результат сохранялся в диагностике, а публикационный путь перебирал только
жёстко заданные `EVERGREEN_BRIEFS`. Поэтому результаты внешних исследований не
могли стать будущими постами.

Теперь `jobs/pets/job.py` использует `collect_source_candidates()` и при
явном `PETS_ALLOW_PRODUCTION_QUEUE=1` — `replenish_verified_queue()`. Без этого
opt-in source-only запуск пишет только во временную кандидатную SQLite и не
изменяет durable production state. Новый слой:

1. выбирает только `editorially_ready` factual briefs;
2. требует исходные факты с допустимой лицензией;
3. не принимает mock-текст;
4. проверяет текст и конкретное изображение;
5. записывает готовый материал в `pets_publication_queue`;
6. исключает `curated_original` и demo-материалы.

Новый factual material не требует добавлять идентификатор в Python allowlist.
Но он всё равно не публикуется до независимого durable-state/Telegram gate.

## Пополнение очереди

Цель очереди — 7 готовых постов; при остатке ниже 5 запускается пополнение.
В SQLite хранится связь queued material с исходными facts, лицензией, фото,
источником и последующим `message_id`. Если подходящих доказательств нет,
возвращается причина `insufficient_verified_factual_briefs`; критерии не
ослабляются. Повтор DOI/PMCID, похожая тема и ранее опубликованный материал
не допускаются.

Текущая реальная доказательная база недостаточна для обещания очереди из 7:
в 3.1.3 был 1 editorially-ready кандидат из 30 уникальных. Механизм пополнения
реализован и проверен на factual fixtures, но production queue намеренно не
заполнялась без разрешённого source-only запуска и отдельного разрешения на AI.

## Обязательные дальнейшие действия перед production

1. Оставить `PETS_PUBLISH=0`, cron выключенным, PR не объединять.
2. Отдельно разрешить безопасный source-only сбор в temporary SQLite и оценить
   реальные кандидаты; никакого GigaChat на этом шаге.
3. После владельческого согласия — лимитированный GigaChat, ручной просмотр
   первых generated drafts и фотографий.
4. Отдельно согласовать миграцию production `pets-state`; она нужна, чтобы
   применить quarantine старых demo записей. История опубликованного №39 и его
   `message_id` сохраняются.
5. Только при наличии проверенной очереди и независимой preflight-проверки
   durable state/прав бота рассматривать включение публикации.
